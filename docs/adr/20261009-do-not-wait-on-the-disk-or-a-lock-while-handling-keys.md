# キーを処理するあいだは、ディスクにもロックにも長く待たない

状態：採用

## 背景

IME は、キーを処理するスレッドで、利用者の打ったものをファイルに書く。辞書登録と削除の行は `custom.tsv` に足し、よく選ぶ候補の記録はフォーカスが移るたびに `selections.tsv` に書く。macOS ではキーの処理がメインスレッドなので、ここで止まると、どのアプリでも打つのが止まる。

- `custom.tsv` に行を足すときは、横の `custom.tsv.lock` を取れるまで待ち続けていた。設定アプリが語を消して `custom.tsv` を書き直しているあいだ、ロックはそちらにある。
- `selections.tsv` は、一時ファイルに書いて置き換える。置き換える前に一時ファイルを `sync_all` でディスクまで書き出していた。macOS ではこれが `F_FULLFSYNC` になり、数百 ms かかることがあった。

`selections.tsv` のロックは、すでに少しだけ待って、取れなければ書かずに次のフォーカスの移動まで持っている。

## 決定

- `custom.tsv` のロックも、少しだけ（50 ms）待って、取れなければその行を書かない。書けなかった行の扱いは、ほかの書き込みの失敗と同じにする。語はメモリでは効いたまま、まだ書いていない行として持ち、次の行を書く前に書き直す。フォーカスが移るときにも書き直す。
- Windows の書き込み用のプロセスは、キーを処理しないので、`custom.tsv` のロックを長く（10 秒）待つ。そこで書けなかった行は、次の行が来るまで書き直さないため。
- IME が書く `selections.tsv` は、これまでどおり一時ファイルに書いて置き換えるが、置き換える前にディスクまで書き出すのを待たない。
- 設定アプリが書くファイル（`custom.tsv` の書き直し、設定ファイルなど）は、これまでどおりディスクまで書き出してから置き換える。キーの処理を止めないため。
- IME が `custom.tsv` に行を足すときも、これまでどおりディスクまで書き出すのを待たない。

## 検討した他の案

- `selections.tsv` を書くのを別のスレッドに移す：ディスクまで書き出す安全さは残るが、ロックは読んでから書き終えるまで持つので、そのスレッドに渡すことになる。書けたかどうかと書いた後のファイルの印を、キーを処理するスレッドに戻して、まだ書いていない選択の扱いに合わせる必要がある。書いている途中で IME が終わればそのぶんは失うので、失う範囲はこの決定と大きく変わらない。
- 書き出しを何回かに一度にする：その一度は同じだけ止まる。
- macOS で `F_FULLFSYNC` でなく `fsync` を使う：短くはなるが、ディスクの速さしだいで止まり、`fsync` だけでは macOS ではディスクに届いたことにならない。
- `custom.tsv` のロックを待ち続けるのをやめ、ロックなしで足す：設定アプリの書き直しと重なると、足した行が消える。

## 結果

- キーを処理するあいだ、ロックを待つのは 50 ms までになり、ディスクへの書き出しは待たない。
- 設定アプリが `custom.tsv` を書き直しているあいだに登録した語は、その場ではファイルに書かれず、次の登録か、フォーカスの移動で書かれる。そのどちらもないまま IME が終わると、その語は失う。
- IME だけが落ちたときは、`selections.tsv` に書いたものは失わない。OS が落ちたときや電源が切れたときは、OS がディスクに書き出していなかった分の選択を失う。ファイルシステムによっては、`selections.tsv` が空や 0 の並びになり、それまでの選択をすべて失うことがある。記録は並べ替えの手がかりで、打つうちにまた覚えるので、そうなることは受け入れる。0 の並びは読めない行として飛ばすので、記録が空から始まるだけになる。
