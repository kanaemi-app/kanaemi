# Windows では外からの操作を書き込み用のプロセスが受ける

状態：採用

## 背景

外からのモードの操作は、IME が待ち受けるローカルの TCP で受ける（20261005-control-the-mode-over-a-local-tcp-connection.md）。macOS と IBus では IME が 1 つのプロセスで動き、そのプロセスがポートを持てる。

Windows の TIP は、入力を受けるアプリのプロセスの中で、UI のスレッドごとに動く。1 つのポートを待ち受けられるのは 1 つのプロセスだけで、フォーカスのある入力欄はどのプロセスにもありうる。ログイン時に起動して動き続ける書き込み用のプロセスはすでにある（20261003-write-user-data-from-a-separate-process-on-windows.md）。

## 決定

- 書き込み用のプロセスが、設定ファイルにポートが書いてあるときに待ち受ける。設定ファイルは、変わっていれば読み直す。
- TIP は、入力欄がフォーカスを得たとき・失ったとき・モードが変わったときに、書き込み用のプロセスへ名前付きパイプで知らせる。書き込み用のプロセスは、最後にフォーカスを得た入力欄とそのモードを覚え、モードを読む要求と見張りには、覚えている値で答える。
- モードを変える要求は、フォーカスのある入力欄の TIP にパイプで渡す。TIP はその UI スレッドでモードを変え、終わったと知らせる。書き込み用のプロセスは、その知らせを待って答える。決めた時間のうちに知らせが来なければ、覚えているモードで答え、TIP はあとから着いた要求ではモードを変えない。
- パイプは辞書の行を受けるパイプとは別に作り、TIP はプロセスごとに 1 本つないだままにする。書き込み用のプロセスがこのパイプを作るのは、設定にポートが書かれてから。
- このパイプを開けるのは、利用者本人と、本人の AppContainer のプロセスだけ。AppContainer には、データの読み書きと作った者を見ることだけを許し、パイプのインスタンスを作らせない。
- TIP は、利用者本人か管理者が作ったパイプにだけつなぐ。書き込み用のプロセスは、各接続に、その接続が知らせた入力欄へのモードしか送らない。
- パイプで受けたモードは、スレッドごとのメッセージ専用ウィンドウにメッセージを送って UI スレッドに渡す。メッセージには中身を載せず、モードはプロセスの中で渡す。

## 検討した他の案

- 各 TIP がポートを待ち受ける：待ち受けられるのは 1 つのプロセスだけで、フォーカスのある入力欄がそこにあるとは限らない。
- フォーカスを得た TIP が、そのたびにポートを取り直す：取り直すたびに接続が切れ、つないだまま使えなくなる。AppContainer の中では、ループバックの通信が既定で制限される。
- モードをウィンドウメッセージの引数で TIP に送る：同じデスクトップのほかのプロセスも同じメッセージを送れ、送り主を確かめられない。AppContainer のアプリから、ほかのアプリの入力欄のモードを変えられてしまう。
- 辞書のパイプと同じく、知らせるたびにつなぐ：書き込み用のプロセスから TIP へ、モードを渡す道がない。
- ポートの設定にかかわらずパイプを作る：外からの操作を使わない利用者でも、入力のあるすべてのプロセスがつなぎ、つなぎ先を待つスレッドを持つ。

## 結果

- 書き込み用のプロセスが動いていないと、Windows では外からの操作が効かない。
- 設定にポートを書くと、入力のある各プロセスに、書き込み用のプロセスとつなぐスレッドが 1 本ずつ増える。ポートを書いた直後と、書き込み用のプロセスを起動し直した直後は、次にフォーカスが動くまで、フォーカスのある入力欄が分からない。
- 応答しないアプリの入力欄では、モードを変える要求に、変える前のモードが返ることがある。
- フォーカスを得た時刻を知らせに入れ、遅れて着いた古い知らせで、覚えている入力欄を置き換えない。
- AppContainer のアプリも、パイプにつないで偽りの知らせを送れる。見張りに偽りのモードを伝えたり、モードを変える要求を自分に向けさせたりはできるが、ほかのプロセスの入力欄のモードは変えられない。
