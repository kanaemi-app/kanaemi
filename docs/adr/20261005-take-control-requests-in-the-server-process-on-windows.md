# Windows では外からの操作を書き込み用のプロセスが受ける

状態：採用

## 背景

外からのモードの操作は、IME が待ち受けるローカルの TCP で受ける（20261005-control-the-mode-over-a-local-tcp-connection.md）。macOS と IBus では IME が 1 つのプロセスで動き、そのプロセスが待ち受けられる。

Windows の IME は、入力を受ける各アプリのプロセスの中で動く。1 つのポートを待ち受けられるのは 1 つのプロセスだけで、フォーカスのある入力欄はどのプロセスにもありうる。ログイン時に起動して動き続ける書き込み用のプロセスは、すでにある（20261003-write-user-data-from-a-separate-process-on-windows.md）。

## 決定

Windows では、書き込み用のプロセスが外からの操作を待ち受ける。

- 各プロセスの IME は、フォーカスとモードが変わるたびに書き込み用のプロセスへ知らせる。書き込み用のプロセスは、最後にフォーカスを得た入力欄とそのモードを覚え、モードを読む要求には覚えている値で答える。
- モードを変える要求は、書き込み用のプロセスが、フォーカスのある入力欄の IME に渡して変えさせる。
- IME と書き込み用のプロセスのつながりは、相手を確かめられる道に限る。書き込み用のプロセスは、利用者本人とその AppContainer のアプリからだけ知らせを受け、IME は利用者本人か管理者が用意した相手にだけつなぐ。書き込み用のプロセスは、ある IME に、その IME が知らせた入力欄のモードしか渡さない。
- 外からの操作を設定していない間は、IME と書き込み用のプロセスをつながない。

## 検討した他の案

- 各プロセスの IME が待ち受ける：待ち受けられるのは 1 つのプロセスだけで、フォーカスのある入力欄がそこにあるとは限らない。
- フォーカスを得た IME が、そのたびに待ち受けを引き継ぐ：引き継ぐたびに接続が切れ、つないだまま使えない。AppContainer の中では、ループバックの通信が既定で制限される。
- 送り主を確かめられない道（ウィンドウメッセージなど）で、IME にモードを渡す：同じデスクトップのほかのプロセスも同じものを送れ、AppContainer のアプリから、ほかのアプリの入力欄のモードを変えられてしまう。
- 設定にかかわらず、IME と書き込み用のプロセスをつなぐ：外からの操作を使わない利用者でも、入力のあるすべてのプロセスがつながりを持ち続ける。

## 結果

- 書き込み用のプロセスが動いていないと、Windows では外からの操作が効かない。
- 外からの操作を設定すると、入力のある各プロセスが、書き込み用のプロセスとつながり続ける。
- 設定した直後と、書き込み用のプロセスを起動し直した直後は、次にフォーカスが動くまで、フォーカスのある入力欄が分からない。
- 応答しないアプリの入力欄では、モードを変える要求に、変える前のモードが返ることがある。
- AppContainer のアプリも、偽りの知らせを送れる。見張る側に偽りのモードを伝えたり、モードを変える要求を自分に向けさせたりはできるが、ほかのプロセスの入力欄のモードは変えられない。
