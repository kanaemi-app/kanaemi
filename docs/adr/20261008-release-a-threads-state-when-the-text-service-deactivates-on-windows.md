# Windows では、スレッドの状態を TIP が非アクティブになるときに手放す

状態：採用

## 背景

Windows の IME（TIP）は、アプリのスレッドごとに、設定・辞書・関数を読み込んだ状態を持つ。これまでは手放す時を決めておらず、スレッドが終わるときか DLL が外されるときに片付けられていた。

Windows では、そのどちらもローダーロックを握ったまま動く。アプリが COM を終えると、IME が断っても DLL は外される（[Windows（TSF）](../references/windows.md)）。そのとき、ローダーロックの中で関数のメモリの回収が走り、ファイルや COM のオブジェクトも閉じていた。ローダーロックの中でこうしたことをすると、ほかのスレッドと待ち合ってアプリが止まったり、先に外された DLL を呼んだりしうる。IME が原因でアプリが止まってはならない。

IME が起こしたスレッドも、DLL が外されたあとに目を覚ますと、もうないコードを動かしてアプリを落とす。

## 決定

- スレッドの状態は、そのスレッドで最後の TIP が非アクティブになるときに手放す。TIP がまたアクティブになったら、読み込み直す。
- 手放す前に、まだ書いていない記録を書く。
- ローダーロックの中では片付けない。スレッドが終わるときや DLL が外されるときに状態がまだ残っていたら、手放さずに置いていく。
- IME が自分のスレッドを起こすときは、DLL をプロセスが終わるまで外させない。

## 検討した他の案

- これまでどおり、スレッドが終わるときや DLL が外されるときの片付けに任せる：ローダーロックの中で関数のメモリの回収やファイルの片付けが走る。
- スレッドが終わるときに、ローダーロックの外で手放す：スレッドの終わりを知る手段は、どれもローダーロックの中で動く。
- 片付けではいつも置いていき、ほかで手放さない：手放す時がなく、DLL を読み込んでは外すアプリでは、外すたびに置いていく分が積み重なる。
- DLL をいつも外させない：DLL を外すときの危うさはなくなるが、スレッドやプロセスが終わるときの片付けは、やはりローダーロックの中で動く。
- フォーカスが外れるたびに手放す：フォーカスはたびたび動き、そのたびに辞書と関数を読み込み直すと、打ち始めが遅れる。

## 結果

- IME を切り替えて戻すと、そのスレッドの状態を読み込み直す。新しいスレッドで初めて打つときと同じだけ待つ。
- 置いていくのは、TIP が非アクティブにならないまま、スレッドが終わるか DLL が外されるときだけ。ふつうは TSF が先に TIP を非アクティブにするので、積み重ならない。
- 手放すときに書けなかった記録は失う。
- IME が自分のスレッドを起こしたプロセスでは、DLL はプロセスが終わるまで外れない。
