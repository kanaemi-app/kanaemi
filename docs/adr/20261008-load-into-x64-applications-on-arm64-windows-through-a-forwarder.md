# ARM64 の Windows では、転送するだけの ARM64X の DLL で x64 のアプリにも読み込ませる

状態：採用

## 背景

Windows の IME（TIP）は COM の DLL で、各アプリのプロセスに読み込まれる。ARM64 の Windows では、ARM64 のアプリと、エミュレーションで動く x64 のアプリが、レジストリの同じ 64 ビット側から DLL を探す。登録できる DLL は 1 つだが、ARM64 の DLL は x64 のアプリが、x64 の DLL は ARM64 のアプリが読み込めない。どちらのプロセスにも読み込めるのは、ARM64X か ARM64EC の DLL だけだ（[Windows（TSF）](../references/windows.md)）。

## 決定

- ARM64 の Windows では、コードを持たず、読み込んだプロセスの種類に応じて別の DLL へ転送するだけの ARM64X の DLL を登録する。ARM64 のプロセスは ARM64 の DLL を、x64 のプロセスは x64 の DLL を、その代わりに読み込む。
- x64 のプロセス向けの転送先は、x64 の DLL にする。ARM64EC にはしない。
- 転送先の DLL は、登録するとき自分ではなく転送用の DLL を登録する。
- x64 と x86 の Windows の作りは変えない。

## 検討した他の案

- ARM64 と ARM64EC のコードを 1 つの ARM64X の DLL にリンクする：Rust のツールチェーンは ARM64X を作れず、cargo が 2 回ビルドしたものを、cargo の外で MSVC のリンカーに渡し直すことになる。rustc がリンカーに渡すものを手で揃え続けなければならず、壊れやすい。
- x64 のプロセス向けを ARM64EC で作る：ネイティブの速さで動くが、ARM64EC の Rust は x64 ほど使われておらず、変換に使う C++ のライブラリも ARM64EC でビルドすることになる。x64 のアプリはもともとエミュレーションで動いており、IME だけ速くしても得るものは小さい。転送先を差し替えるだけで、あとから移れる。
- ARM64 の DLL だけを登録する：x64 のアプリで使えない。
- ARM64 と x64 を別の入力方式として登録する：利用者に同じ入力方式が 2 つ見え、アプリの種類によって選び分けることになる。

## 結果

- ARM64 のインストーラーは、転送用の DLL と、その転送先の DLL を入れる。
- 転送用の DLL を作るのに、MSVC の ARM64/ARM64EC のビルドツールが要る。
- x64 のアプリの中では、IME もエミュレーションで動く。
