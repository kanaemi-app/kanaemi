# Fcitx5 では、薄い C++ の層の後ろで、Fcitx5 のプロセスの中で動かす

状態：採用

## 背景

Fcitx5 の入力方式は、Fcitx5 のプロセスに読み込まれる共有ライブラリのアドオンで、C++ のクラスを継承して作る。IBus のように、別のプロセスのエンジンへキーを渡す仕組みはない。Kanaemi の処理は Rust で書かれている。

## 決定

Fcitx5 では、Fcitx5 が見るエンジンだけを C++ で書き、受けたイベントを C の関数で Rust に渡す。Rust の部分も同じアドオンのライブラリに入り、Fcitx5 のプロセスの中で動く。

- C++ の層は何も決めない。イベントを渡し、返ってきたものを表示するだけにする。
- Rust のパニックは、Fcitx5 に返す前にすべて止める。

## 検討した他の案

- C++ のアドオンは取り次ぐだけにし、Rust の部分を別のプロセスで動かす：Kanaemi が落ちても Fcitx5 は残る。しかし、キーのたびにプロセスをまたいで答えを待つことになり、プロセスの起動と終わりの面倒も C++ の側に要る。
- アドオンをすべて C++ で書く：Kanaemi の処理を、OS ごとに書き直すことになる。

## 結果

- Kanaemi が止まると、Fcitx5 も止まり、すべてのアプリで入力できなくなる。
- アドオンは、それを読み込む Fcitx5 と同じライブラリに対してビルドする。
- IBus のエンジンと Fcitx5 のアドオンは、キーや表示の扱いを Rust の部分で共有できる。
